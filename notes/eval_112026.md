# Fimod — Evaluation, November 2026

- **Date:** 12 November 2026
- **Status:** evaluation and local measurements, not a commitment. `ROADMAP.md` stays the canonical planning source.
- **State evaluated:** branch `feat/monty-1.6.0` at `3bd778d` (fimod 0.13.0, Monty 1.6.0, Rust 1.99.1). Line numbers below refer to that commit.
- **Scope:** vision, position against comparable tools, weaknesses, and how to make fimod fast on large inputs.

## Summary

The maintainer set the performance priority during this evaluation: **throughput on large inputs comes before startup time**. The standard build targets CI and should be as fast as is reasonable there. The fast build targets absolute performance, possibly for data-engineering use.

Main findings:

1. On large inputs the limit is not the Python VM. It is the whole-document model and the conversions around the VM. Throughput of the fast build drops from 49 MB/s to 26 MB/s between 40 MB and 161 MB of JSON, and memory reaches 3.6 GiB for a 161 MB input.
2. Building the Monty value directly from the input text, and serializing the result directly, removes about 40 % of the time with no behaviour change.
3. Processing records in batches (the execution strategy for the `--stream` idea) gives 1.6 to 1.7 times the current throughput on one thread with about 30 times less memory. In parallel it reaches 346 MB/s on 8 threads, but only after the global memory counter stops being updated on every allocation.
4. `opt-level = 2` is as fast as `opt-level = 3` and 36 % faster than the current `opt-level = "z"`, for 1.5 MB more after UPX.
5. Several correctness defects were found on the way; the most limiting one is that YAML input fails above 250,000 nodes.

Decision recorded in section 5: everything that depends on batch execution, parallelism included, is deferred to the `--stream` work package.

## 1. Vision

The thesis is clear and consistent across `VISION.md` and `ROADMAP.md`: Python syntax, a single binary, Rust as the trust boundary, no install. The roadmap aims at the right differentiator, the path "write, test, publish, pin, verify, run in CI". Format conversion is the entry point; tested and shared molds are the lasting value.

Three statements in the repository no longer match reality:

| Where | Statement | Observed |
| --- | --- | --- |
| `notes/VISION.md` | Monty has no classes and no `match` | Classes, `dataclass` and `match` all run on Monty 1.6.0 |
| `notes/perf-baseline.md` line 46 | A direct JSON-to-Monty input path was dropped because Monty enables `serde_json/arbitrary_precision` | Monty no longer depends on `serde_json`; the feature is off (`cargo tree -e features -i serde_json`) |
| `README.md` | The fast build is 15 to 25 % faster | Measured 32 to 38 % faster on filter, CSV and sort workloads |

## 2. Position against comparable tools

The "loses" column for jq and yq is measured where a number is given; the rest is general knowledge of those tools.

| Against | What fimod brings | Where fimod loses |
| --- | --- | --- |
| jq | Python instead of a DSL, every format, molds and registry, fixture tests | jq is installed everywhere, uses 4 times less memory, and filters NDJSON as a stream (3.4 MiB against 321 MiB) |
| yq | About twice as fast on YAML to JSON (0.12 s against 0.26 s on 10,000 records) | yq reads multi-document YAML; fimod drops comments and anchors, which hurts the "patch a YAML config" use case |
| Python with `uv run` | Deny-by-default sandbox, small binary, no interpreter download | Full CPython and PyPI; the "no Python install" argument weakens as uv spreads |

Two strengths are not combined by any of these tools: testable molds distributed through git registries, and the fact that an AI agent writes Python far more reliably than jq, here inside a sandbox. Multi-file mode is also strong: 200 small files in one process take 16 ms.

## 3. Weaknesses

### Defects found while testing

| Defect | Observation | Location and likely fix |
| --- | --- | --- |
| YAML input capped at 250,000 nodes | A 1.75 MB list (about 22,700 records of 5 fields) fails with `budget breached: Nodes { nodes: 250001 }` | `DataFormat::parse` in `src/format.rs` (line 152) uses the default `serde-saphyr` budget; `from_str_with_options` accepts an explicit one |
| Multi-document YAML rejected | `a: 1`, `---`, `a: 2` fails, with or without `-s` | Same call; `serde_saphyr::from_multiple` exists |
| TOML datetimes corrupted | `started = 2024-01-02T03:04:05Z` reaches the mold and the output as `{"$__toml_private_datetime": "..."}` | `toml::from_str` into `serde_json::Value` (line 153) leaks the crate's private representation |
| Output writes are not atomic | `--in-place` and `-o` truncate then write; an interruption leaves a truncated file | `fs::write` in `output_result` and `write_bytes_to` (`src/pipeline.rs` lines 1391 and 1492); the identity streaming path already writes to a temporary file and renames |
| Integers beyond 64 bits lose precision silently | `12345678901234567890123` becomes `1.2345678901234568e+22`; `1e400` is a parse error | JSON number handling in `serde_json` without arbitrary precision |
| Error traces expose internals | Traces show the wrapper line `transform(data, args=args, ...)` and `mold.py` instead of the mold path; a syntax error in `-e` points at the wrapper line | `execute_mold_with_chain_start` in `src/engine.rs` |

### Structural weaknesses

- **Memory.** 321 to 546 MiB for a 7.87 MB input (roughly 43 to 73 times), and 3.6 GiB for 161 MB. By extrapolation, a 300 MB file does not fit on a 7 GB CI runner.
- **No streaming for transforms.** Only the exact identity conversion `-e data` streams.
- **Fidelity.** Comments and anchors are lost in YAML and TOML. `VISION.md` accepts this trade-off, but it weighs on the configuration-patching audience.
- **Dependency on Monty.** The version is pinned exactly and the `unstable` API is used. On 1.6.0, generators (`yield`) are not supported and the `statistics`, `string` and `urllib` modules are missing.
- **CSV typing.** Every CSV value is a string, so `r["score"] > 30` needs an explicit `int()`.
- **Rust helpers are slower than native Python on large lists** (section 4.7).
- **Project maturity.** One maintainer, nine months of history, no presence in package managers.

## 4. Performance

### 4.1 Method

- **Machine:** AMD Ryzen AI 9 HX 370 (4 fast cores, 8 compact cores, 24 threads), 15 GB RAM, Linux WSL2 x86_64. Numbers are a local snapshot, not a portable promise.
- **Data:** records shaped `{"id", "name", "active", "score", "team"}`. 100,000 records are 7.87 MB of JSON; 500,000 are 39.8 MB; 2,000,000 are 161.4 MB.
- **Binaries:** native builds of the repository profiles, without UPX unless stated. "Standard" is `opt-level = "z"`; "fast" is `opt-level = 3`. These are not the musl release artifacts.
- **CLI timings:** `hyperfine`, median, pinned to one core with `taskset -c 2`. Peak memory is resident set size from `/usr/bin/time`, in MiB or GiB.
- **In-process timings:** a probe crate outside the repository links the `fimod` library, times each stage (median of 5 to 7 runs) and records peak heap (in MB) through the same counting allocator as fimod. It also holds the prototypes. At 100,000 records the sum of its stages (277 ms) matches the CLI (280 ms).
- **Reference tools:** jq 1.8.1, yq 4.53.2.

### 4.2 Where the time goes

Filter `[r for r in data if r["active"]]` on 100,000 records, milliseconds.

| Stage | Standard | Fast |
| --- | ---: | ---: |
| Parse JSON text into `serde_json::Value` | 61 | 39 |
| Convert `Value` into `MontyObject` | 62 | 40 |
| Load the data into the VM (measured with `len(data)`) | 70 | 44 |
| Whole VM stage for the filter (load, loop, result) | 110 | 72 |
| Convert the result into `Value` (full 100,000 records) | 61 | 41 |
| Serialize `Value` as indented JSON (full 100,000 records) | 26 | 11 |
| Compile a mold | 0.01 | 0.01 |

Three causes stand out:

- `json_into_monty` (`src/convert.rs` line 105) builds one small graph per value, then merges it into its parent at every nesting level. Each leaf costs a heap allocation and every node is moved once per level.
- Indented JSON, the default output format, is the only JSON output without a direct serialization path (`process_single_input`, `src/pipeline.rs` line 1225). It goes through a full `Value` tree.
- The direct serializer copies every dictionary key into a new `String` (`src/convert.rs` line 240).

### 4.3 Behaviour as the input grows

Same filter, compact JSON output, one core. Throughput in MB/s, with peak memory in GiB in parentheses.

| Input | jq | Standard | Fast |
| --- | ---: | ---: | ---: |
| 7.9 MB | 35 (0.08) | 32 (0.31) | 49 (0.31) |
| 39.8 MB | 34 (0.37) | 31 (1.1) | 50 (1.1) |
| 79.7 MB | 35 (0.75) | 26 (1.9) | 35 (2.0) |
| 161.4 MB | 36 (1.5) | 19 (3.4) | 26 (3.6) |

jq stays flat. fimod is flat up to 40 MB and then loses almost half its throughput, as its memory footprint reaches several gigabytes.

### 4.4 Prototypes

All prototypes produce values equal to the current code on the test data. Times are for 100,000 records, milliseconds.

| Prototype | Replaces | Standard | Fast |
| --- | --- | ---: | ---: |
| JSON text straight into one Monty arena, object keys stored once and shared | Parse plus convert (123 / 79) | 31 | 18 |
| CSV straight into one arena, header nodes shared by all rows | `csv_to_monty` (100 / 68) | 19 | 10 |
| Indented JSON serialized from the Monty value, keys borrowed | Convert plus serialize (88 / 52) | 29 | 11 |
| Compact JSON with borrowed keys | Current direct path (30 / 14) | 23 | 7 |

Two levels of change are possible for JSON input. Keeping the `Value` tree and only rewriting the converter to push into one arena gives 88 ms (standard) and 56 ms (fast) for the input stage, about 28 % less than today. Reading the text straight into the arena, the first row above, gives 31 and 18 ms, about 75 % less. On the whole filter command with indented output, that is roughly 12 % against 36 %, derived by subtracting stage times.

Sharing the keys cuts the arena from 1,100,001 to 600,006 nodes and makes the VM load about 15 % faster. The input prototype is a serde `DeserializeSeed` that pushes nodes in post-order into a single `MontyGraph` and wraps it with `unstable::object_from_graph`.

End to end on 39.8 MB (500,000 records), milliseconds:

| Pipeline | Standard | Fast | Peak heap |
| --- | ---: | ---: | ---: |
| Current code (CLI) | 1,292 | 803 | 709 MB |
| Direct input and output, whole document | 768 | 472 | 612 MB |
| Batches of 1,000 records, stream contract, 1 thread | 807 | 475 | 21 MB |
| Batches of 1,000 records, stream contract, 8 threads | not measured | 115 | not measured |

The 21 MB are mostly the output, which the prototype keeps in memory before returning it. The 8-thread figure requires the allocator change described in section 4.5.

### 4.5 Stream mode

Batch processing is not a new feature idea. It is the execution strategy for a contract that already exists twice in the project:

- `notes/stream.md` (added in `79ae585`, removed in `cb2f6a4`) designed a `--stream` flag: `data` is one unit (a CSV row, an NDJSON value, a text line), returning `None` skips the unit, and optional `initialize(headers)`, `transform(data, ctx)` and `finalize(ctx)` carry state.
- `ROADMAP.md` 0.12, "record-scale processing", restates it as `transform(record, ...)` applied to each record.

That contract answers the two questions batch mode raises: a record is dropped by returning `None`, and aggregation goes through `ctx` and `finalize`.

What the measurements add:

- **The engine must batch internally.** One VM run per unit costs 16 µs per unit in the fast build and 26 µs in the standard build, which is 8 to 13 seconds for 500,000 units. Looping over a batch inside one VM run costs 1 to 1.6 µs per unit, input and output included. The mold still sees one unit at a time.
- **Batch size.** 1,000 units was the best of 100, 1,000 and 10,000.
- **JSON arrays can stream too.** The note limited streaming to line-oriented formats. A top-level JSON array can be read element by element, as the identity path already does; the prototype figures above use a JSON array.
- **State across batches is unmeasured.** `ctx` must survive between VM runs, either by passing it in and out of each batch or by keeping one Monty session alive. Neither was tested.
- **Parallelism only fits stateless molds.** A mold without `ctx`, `initialize` or `finalize` can run its batches on several threads, with outputs reassembled in input order. This maps onto the two variants: sequential in the standard build, parallel in the fast build.

Parallel scaling, fast build, NDJSON, stream contract, 500,000 records, milliseconds:

| Threads | Global memory counter (as today) | Counter disabled |
| ---: | ---: | ---: |
| 1 | 485 | 461 |
| 4 | 208 | 159 |
| 8 | 239 | 115 |

`CountingMiMalloc` (`src/mem_limit.rs` line 40) updates one shared atomic on every allocation and release. With several threads that single cache line becomes the bottleneck: scaling stops near 2.3 times. Without it, 8 threads reach 4 times (346 MB/s). A parallel fast build therefore needs per-thread accounting flushed in blocks, which makes `sandbox.max_memory` approximate by a bounded amount.

After the fimod-side changes, about two thirds of a batch's time is spent inside Monty (loading values, running, returning values), estimated by subtracting the input and output stages. That part can only improve upstream.

### 4.6 Build profiles

CLI, one core, milliseconds. Sizes in MB.

| `opt-level` | Raw | After `upx --best --lzma` | Filter 100k | CSV filter 100k | Sort 100k | Filter 500k |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| `"z"` (standard today) | 11.8 | 3.8 | 249 | 266 | 342 | 1,284 |
| `"s"` | 13.3 | 4.2 | 206 | 212 | 276 | 967 |
| `2` | 17.7 | 5.3 | 164 | 183 | 226 | 816 |
| `3` (fast today) | 18.8 | 5.6 | 160 | 182 | 227 | 791 |

Level 2 equals level 3 within noise. A hybrid profile (hot crates at level 3, everything else at `"z"`) is not worth having: 18.4 MB for the same speed, because Monty itself carries most of the size.

### 4.7 Rust helpers and host calls

CLI, standard build, 100,000 records.

| Operation | Time | Peak memory |
| --- | ---: | ---: |
| `jq 'sort_by(.score)'` | 461 ms | 88 MiB |
| `it_sort_by(data, "score")` | 583 ms | 546 MiB |
| `sorted(data, key=lambda r: r["score"])` | 343 ms | 367 MiB |
| `[r["name"] for r in data]` | 217 ms | 307 MiB |
| `[dp_get(r, "name") for r in data]` | 492 ms | 306 MiB |

- A helper that receives the whole dataset pays for two extra copies in and one out. `run_loop` (`src/engine.rs` line 1052) copies every argument with `to_owned`, which alone costs 31 ms here and can be avoided by taking ownership of the call arena.
- Each host call costs about 2.5 µs in the standard build (1.5 µs in the fast build), roughly ten times a native per-row operation. Most of it is Monty's suspend and resume, not fimod code.

### 4.8 Startup and packaging

Recorded for completeness; not a priority for the standard build.

- `fimod --version` takes 3 ms uncompressed and 216 ms after `upx --best --lzma`, the packing used for standard and slim release artifacts on Linux and Windows.
- A shell loop over 200 small files takes 0.65 s uncompressed and 38.5 s with the packed binary (jq: 0.35 s). One fimod batch invocation for the same 200 files takes 16 ms uncompressed.
- The uncompressed standard binary is 3.76 MB under `xz -9`, the same as the UPX-packed binary.

### 4.9 Not worth doing

- **A compiled-mold cache** (ROADMAP 0.12, item 4). Compiling a mold takes about 0.01 ms.
- **`--jobs` for batches of small files.** 200 files already take 16 ms in one process.
- **A hybrid build profile** (section 4.6).
- **`target-cpu=x86-64-v3` for the fast build.** Differences from the current fast binary stayed within noise (about ±10 %; the machine was busy during that run).
- **A SIMD JSON parser.** With the direct reader, parsing and arena building are about a fifth of the filter command; the VM dominates.

## 5. Recommended order

**Decision (maintainer, 12 November 2026):** everything that depends on batch execution belongs to the `--stream` work package and is deferred. Near-term performance work is limited to changes that keep the whole-document model.

Now, with the whole-document model unchanged:

1. **Direct input and output.** Text straight into the arena for JSON, NDJSON and CSV with shared keys; direct indented output; borrowed keys. No behaviour change; protect with parity tests. A later stream reader fills each batch with the same arena builder, so this work carries over.
2. **Standard profile at `opt-level = "s"`** (decided, section 6). Users who need more speed are pointed to the fast build.

Scope approved for the first phase (12 November 2026), specified in `notes/spec-perf-phase1.md`: the single-arena converter that keeps the `Value` tree, direct indented output with borrowed keys, and `opt-level = "s"`. Reading text straight into the arena, shared keys and the CSV rewrite are not part of that phase.

The maintainer requires that the direct input path ships with tests that harden Monty upgrades, because it builds the arena through Monty's `unstable` API and relies on shared key nodes. Planned coverage: differential tests against the retained `Value` path (fixed corpus plus generated documents), contract tests through the VM in the style of `test_monty_graph_shared_values_and_cycles_at_json_boundary` (identity round trip, mutating one record leaves the others intact), a CLI comparison with `--debug`, which keeps the `Value` path, and key sharing behind a single switch.

Later, in the `--stream` work package:

3. **`--stream` itself.** Specify from the removed `notes/stream.md` and the ROADMAP 0.12 criteria, then implement with internal batches, sequential first. JSON array streaming and state across batches belong here.
4. **Parallel batches in the fast build.** Stateless streams only, with per-thread memory accounting.

Consequence of the split: the near-term work removes about 40 % of the time but does not bound memory. On the 39.8 MB test, peak heap only goes from 709 MB to 612 MB. The prototypes were not measured above 40 MB, so the throughput drop on larger inputs (section 4.3) should be assumed to remain until stream mode exists.

The defects in section 3 are independent of both tracks and small.

## 6. Decisions for the maintainer

Needed for the near-term work:

- Standard build `opt-level`: **decided on 12 November 2026: `"s"`** (4.2 MB after UPX, 17 to 25 % faster than `"z"`). `VISION.md` cites `opt-level = "z"` in its accepted trade-offs and needs the matching edit when the change lands.
- Whether JSON, NDJSON and CSV input may bypass `serde_json::Value`. `ARCHITECTURE.md` states that every `parse()` returns a `Value`; the existing `csv_to_monty` path is the precedent.
- How to position Rust helpers on large lists: steer the documentation towards native Python, or add helpers that take a whole list in one call.
- Whether to correct the three drifted statements in section 1.

Deferred with the `--stream` work package:

- The `--stream` surface: confirm the `notes/stream.md` contract, decide whether JSON arrays are included, choose how `ctx` survives between batches, and define fail-fast and partial-output behaviour.
- Whether the fast build becomes "the parallel build", since level 2 and level 3 are equivalent.
- Whether `sandbox.max_memory` may become approximate in exchange for parallel scaling.

## 7. Limits of this evaluation

- One machine under WSL2, one record shape (five short fields). Wide or deeply nested records were not tested.
- The prototypes live in a probe crate, not in fimod. Equality with the current code was checked on the test data only. Duplicate keys in a JSON object need a dedicated parity test, because the direct builder keeps both entries where `serde_json::Map` keeps the last.
- At 500,000 records the "current code" row comes from the CLI while prototype rows are in-process.
- Not measured: profile-guided optimization (the toolchain has no `llvm-profdata`), the CSV output path on its own, a persistent Monty session for stream state, and parallel scaling of the standard build without the global counter.
- The yq comparison uses `yq -o json`. yq's `-I0` flag is pathologically slow on long sequences (58 s for 20,000 records) and was excluded.

## Appendix — Reproducing

Dataset generator:

```python
import json

def row(i):
    return dict(id=i, name=f"user-{i:06}", active=i % 2 == 0,
                score=(i * 7919) % 100000, team=f"team-{i % 16}")

for n, name in ((100_000, "users100k"), (500_000, "users500k"), (2_000_000, "users2m")):
    with open(f"{name}.json", "w") as f:
        f.write("[" + ",".join(json.dumps(row(i), separators=(",", ":")) for i in range(n)) + "]")
```

CLI comparison (replace the binary to compare profiles):

```bash
hyperfine -N --warmup 2 --runs 9 \
  "taskset -c 2 jq -c '[.[] | select(.active)]' users500k.json" \
  "taskset -c 2 target/release/fimod s --sandbox-file= -i users500k.json -e '[r for r in data if r[\"active\"]]' --output-format json-compact"
```

Build variants without editing `Cargo.toml`:

```bash
CARGO_TARGET_DIR=/tmp/fimod-o2 cargo build --release --locked --config profile.release.opt-level=2
```

The probe crate (stage timings, prototypes, batch and parallel drivers) and the benchmark scripts are kept as an untracked local copy under `tmp/perf-probe-2026-11/` on the maintainer's machine. They are not part of the repository.
