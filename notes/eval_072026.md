# Évaluation de Fimod — juillet 2026

- **Date de l'évaluation :** 10 juillet 2026
- **Checkout évalué :** `main`, `1a977ce`, tag `v0.9.0`
- **Périmètre :** positionnement produit, visibilité publique, qualité du code,
    correctness, robustesse, sécurité, DRY, performance, tests/CI, documentation
    et proposition de roadmap.

Cette note décrit l'état observé. Sa roadmap est une **proposition**, pas un
engagement déjà accepté. Le checkout ne contient plus de `notes/ROADMAP.md` et
aucun développement post-`v0.9.0` n'est engagé sur `main`.

## Findings prioritaires

### R1 [Majeur] Une chaîne dynamique peut ne jamais finir malgré `max_duration`

La limite de durée annoncée comme protection de l'invocation est en réalité
recréée pour chaque étape Monty. En parallèle, une étape peut en ajouter une
autre sans plafond global : `execute_chain()` boucle sur une longueur mutable
(`src/pipeline.rs:174-175`), insère ou ajoute les étapes à
`src/pipeline.rs:268-280`, puis chaque `execute_mold()` recrée un
`LimitedTracker` à `src/engine.rs:893-903`.

Reproduction bornée par le processus hôte :

```bash
timeout --signal=TERM --kill-after=1s 2s \
  ./target/debug/fimod shape --no-input \
  --arg 'loop=(pipeline.append(Step.create(expr=args["loop"])), data)[1]' \
  -e '(pipeline.append(Step.create(expr=args["loop"])), data)[1]'
```

Résultat : aucune sortie, arrêt externe avec le code `124` après deux secondes.

**Impact :** un mold dynamique récursif, même par erreur, peut consommer CPU et
mémoire indéfiniment. Cela contredit la promesse de limite par invocation du
README (`README.md:407`).

**Correction minimale :** ajouter un plafond global d'étapes injectées et une
deadline/budget partagé par toute la chaîne, puis tester explicitement
l'auto-injection.

### R2 [Majeur] Les grands entiers JSON sont altérés ou changent de type

La frontière `serde_json::Value` → `MontyObject` essaie `i64`, puis passe
directement à `f64` (`src/convert.rs:58-66` et `src/convert.rs:86-93`). Au retour,
un `BigInt` supérieur à `i64::MAX` est sérialisé comme chaîne
(`src/convert.rs:115-121`), alors que la référence promet des entiers de précision
arbitraire (`docs/reference/monty-engine.md:31`).

```bash
printf '%s\n' '18446744073709551615' \
  | target/release/fimod s -e 'data + 0' --output-format json-compact
# 1.8446744073709552e+19

target/release/fimod s --no-input \
  -e '18446744073709551615' --output-format json-compact
# "18446744073709551615"
```

**Impact :** corruption silencieuse d'identifiants, compteurs ou montants JSON
valides ; le second cas conserve les chiffres mais change le type public.

**Correction minimale :** centraliser la conversion numérique, traiter `u64`
avant `f64`, utiliser `MontyObject::BigInt` lorsque nécessaire et reconstruire
un nombre JSON quand il tient dans `u64`. Couvrir `2^53+1`, `i64::MAX+1`,
`u64::MAX` et un entier au-delà du domaine JSON natif retenu.

### R3 [Bloquant release] La gate de dépendances est rouge

`rtk task lint` passe `cargo fmt --check` et Clippy, puis échoue dans
`cargo-deny` sur :

- [`RUSTSEC-2026-0190`](https://rustsec.org/advisories/RUSTSEC-2026-0190.html),
    `anyhow 1.0.102` (`Cargo.lock:105-106`) ;
- [`RUSTSEC-2026-0204`](https://rustsec.org/advisories/RUSTSEC-2026-0204.html),
    `crossbeam-epoch 0.9.18` (`Cargo.lock:587-588`).

La nuance est importante : Fimod utilise `downcast_ref`, pas le
`downcast_mut` concerné par le premier avis, et `crossbeam-epoch` arrive par
l'arbre de test `assert_fs`. Aucun chemin d'exploitation Fimod n'a donc été
confirmé ; le blocage est néanmoins réel pour la politique CI/release du dépôt.

Le correctif retenu doit être préparé localement, sans reprendre une PR
Dependabot : monter `anyhow` au minimum à `1.0.103`, obtenir
`crossbeam-epoch >= 0.9.20` directement ou via la dépendance de test qui
l'introduit, rafraîchir le lockfile, puis repasser lint, tests et audit. Les
autres upgrades compatibles peuvent être regroupés dans ce travail après tests
ciblés.

### R4 [Majeur produit] Les textes publics et les sources de vérité divergent

Ce n'est pas seulement de la cosmétique : plusieurs affirmations diminuent la
crédibilité du positionnement.

- `docs/guides/comparison.md:25` dit que yq ne sait pas sortir du CSV, alors que
    sa documentation officielle couvre l'[encodage, le décodage et le round-trip
    CSV/TSV](https://mikefarah.gitbook.io/yq/usage/csv-tsv).
- La matrice affirme que jq et yq n'ont pas d'exit status
    (`docs/guides/comparison.md:66`) ; les deux exposent `--exit-status`
    ([jq](https://jqlang.org/manual/v1.7/#invoking-jq),
    [yq](https://mikefarah.gitbook.io/yq/commands/evaluate)).
- `fancy-regex` est présenté comme PCRE2. La crate documente une syntaxe
    hybride fondée sur `regex` et visant notamment une compatibilité Oniguruma,
    pas le moteur PCRE2
    ([documentation officielle](https://docs.rs/fancy-regex/latest/fancy_regex/)).
- Le README parle d'un binaire Windows « signed » (`README.md:99`), mais la
    release `v0.9.0` fournit des checksums SHA-256, pas d'asset de signature.
- « Safe for remote and untrusted molds » (`README.md:407`) est trop absolu au
    regard du non-but explicite « threat-model-grade sandboxing of hostile code »
    (`notes/VISION.md:43`) et du finding R1.
- Le README et le site disent que tout breaking change augmente la version
    majeure (`README.md:455`, `docs/index.md:248`), tandis que le workflow impose
    un bump mineur avant 1.0 (`notes/release-workflow.md:30-33`).
- L'exemple copiable `FIMOD_VERSION=0.1.0` (`README.md:49`) peut installer une
    très vieille version par accident.

Les notes internes ont aussi dérivé : `notes/ARCHITECTURE.md:142` reporte encore
le sandbox à 0.5.0, `notes/CODE_LAYOUT.md:106` annonce `hs_sha512` et
`hs_blake3` qui n'existent pas, et plusieurs fichiers renvoient vers une
`notes/ROADMAP.md` absente.

## Positionnement produit

### La meilleure phrase

> **Un petit mais puissant couteau suisse de transformation pour la CI et les
> configs : formats multiples et HTTP, logique Python-shaped sans Python
> installé, transforms partageables par molds, exécution contrôlée par Rust.**

La thèse actuelle, « Python-powered molding without Python installed », est
forte. Le produit est le plus convaincant quand il résout les petits traitements
qui finissent aujourd'hui en `python3 -c`, en chaînes `curl | jq | sed`, ou en
scripts copiés entre pipelines.

### Ce qui différencie vraiment Fimod

1. **Le faisceau de capacités, pas une case de matrice isolée** : JSON, YAML,
    TOML, CSV, NDJSON, texte et HTTP dans un binaire compact.
2. **Une syntaxe familière** : un goût Python et des helpers Rust, sans inventer
    un nouveau DSL, tout en disant clairement que Monty n'est pas CPython.
3. **La réutilisation contrôlée** : molds, registries Git/HTTP, métadonnées,
    args typés et runner de fixtures.
4. **Une bonne forme CLI/CI** : stdin/stdout, batch, slurp, chaînes, exit codes,
    stderr propre, binaire autonome.

Le registre, HTTP, le petit binaire et le sandbox forment un positionnement plus
défendable que « meilleur que jq/yq ». Fimod peut les compléter ou les remplacer
sur certains workflows sans prétendre gagner chaque ligne d'une matrice.

### Frontières à conserver

Les non-buts de `notes/VISION.md` sont cohérents et doivent rester visibles :
pas de daemon HTTP, pas de PyPI arbitraire, pas de promesse CPython complète,
pas de registre central ni de télémétrie serveur, pas de sandbox multi-tenant
contre du code hostile.

### Performance mesurée localement

Commande :

```bash
rtk mise exec -- cargo test --release --test performance -- --ignored --nocapture
```

Les six tests passent :

| Scénario                                    |  Médiane |  Budget / comparaison |
| ------------------------------------------- | -------: | --------------------: |
| JSON parse + Monty + compact, 20 000 lignes | 134,1 ms |         budget 350 ms |
| CSV direct Monty + serialize, 20 000 lignes |  70,3 ms |         budget 450 ms |
| Chaîne de 3 molds, 1 500 lignes             |  35,0 ms |         budget 250 ms |
| Filtre JSON CLI                             | 123,5 ms |  1,45× le temps de jq |
| Filtre lignes CLI                           |  40,9 ms | 2,67× le temps de awk |
| YAML → JSON compact                         | 109,6 ms |  0,88× le temps de yq |

Ce run montre un outil compétitif pour sa richesse fonctionnelle, pas un moteur
à présenter comme systématiquement plus rapide. Les valeurs dépendent de la
machine ; elles servent surtout de budget de régression. La note
`notes/perf-baseline.md` s'arrête à 0.7.x et doit être recalée sur 0.9 standard,
fast et identity native.

**Suivi local 0.9.1 :** la baseline contient désormais des mesures `release` et
`release-fast` sur 20 000 entrées, ainsi que les conversions identité. La
matrice 10/100/1 000 Mo avec RSS reste à produire.

### Axe performance : conversions de gros volumes

Le cas JSON array → JSONL/NDJSON exact n'est plus un trou fonctionnel : avec une
seule expression `-e data`, Fimod 0.9 utilise déjà un chemin Rust natif qui lit
et sérialise un élément à la fois. La mémoire est donc bornée par le plus gros
élément, pas par la taille totale du fichier. Le passage par Monty reste
nécessaire dès que l'expression transforme réellement le tableau.

Un diagnostic local complémentaire a utilisé 200 000 objets : JSON et NDJSON
de 15,3 Mo, CSV de 6,9 Mo. Les temps sont indicatifs ; le RSS est le pic remonté
par `/usr/bin/time -v`.

| Conversion                                              | Temps observé | Pic RSS | Lecture                                                                 |
| ------------------------------------------------------- | ------------: | ------: | ----------------------------------------------------------------------- |
| JSON array → NDJSON, identité native                    |        228 ms |  14 MiB | bon chemin actuel ; environ 3× plus rapide que la copie Monty mesurée   |
| JSON array → CSV, identité native                       |        260 ms |  14 MiB | bon chemin actuel ; mémoire indépendante de la taille totale            |
| JSON array → NDJSON, copie forcée via Monty             |        677 ms | 685 MiB | coût CPU et surtout mémoire très élevé pour un résultat équivalent      |
| NDJSON → JSON compact, identité                         |        360 ms | 266 MiB | tableau complet encore matérialisé ; candidat direct au streaming       |
| CSV → NDJSON, identité                                  |        320 ms | 256 MiB | lignes complètes encore accumulées ; candidat direct au streaming       |

**Suivi local 0.9.1 :** NDJSON → JSON/JSON compact utilise maintenant un chemin
streaming borné par la plus grande ligne. Le benchmark courant sur 20 000 lignes
mesure 45,765 ms en `release` et 29,044 ms en `release-fast`. Le tableau ci-dessus
reste la mesure initiale sur 200 000 objets ; son RSS doit être remesuré avec le
nouveau chemin.

Le premier objectif n'est donc pas de réécrire le fast path JSON → JSONL, mais
d'étendre la mémoire bornée aux conversions symétriques qui en sont encore
privées. Le hot loop actuel JSON → NDJSON matérialise toutefois chaque ligne en
`serde_json::Value` avant de la resérialiser : il reste une optimisation CPU et
allocations possible, à décider seulement après profilage.

#### Roadmap performance proposée

- [x] Ajouter les cas d'identité aux tests de performance et établir une
      baseline locale 0.9.1 `release` / `release-fast` sur 20 000 entrées.
- [ ] Compléter la baseline sur 10, 100 et 1 000 Mo, vers `/dev/null`, avec
      débit, temps de démarrage et pic RSS.
- [x] Livrer NDJSON → JSON/JSON compact en streaming, avec parité stricte des
      résultats et erreurs couvertes par les tests.
- [ ] Livrer CSV → NDJSON en streaming après extraction de la logique de headers,
      puis décider NDJSON ↔ CSV sur un contrat de schéma explicite.
- [ ] **Profiler puis alléger JSON array → NDJSON.** Tester des buffers explicites
      de 64 à 256 Kio, puis un transcodage Serde/token sans arbre `Value` par
      ligne. Une copie brute de `RawValue` ne suffit pas : un élément JSON
      indenté peut contenir des retours à la ligne et produire un NDJSON
      invalide. Ne considérer `simd-json` ou une nouvelle dépendance qu'après
      preuve que le parseur domine.
- [ ] **Définir un mode record streaming séparé pour les vraies transforms.** Si
      les usages le demandent, compiler le mold une fois et appliquer
      `transform(record)` à chaque objet JSONL/CSV. Ce mode doit être explicite :
      réinterpréter silencieusement `data` d'un tableau vers une ligne casserait
      les molds existants. Ordre, état, erreurs partielles, `pipeline` dynamique
      et limites Monty doivent être spécifiés avant le code.

Cette séquence maximise d'abord le gain mémoire certain. Le parallélisme batch
et les micro-optimisations du binaire standard viennent après : ils ne corrigent
pas les centaines de Mio consommées par les chemins qui matérialisent encore le
document complet.

### Dette structurelle utile à traiter

- Extraire un planificateur unique des destinations batch avant de corriger
    séparément raw, transformé, URL et in-place.
- Unifier la lecture/détection/parsing entre pipeline normal et identité native,
    en conservant les optimisations derrière des tests de parité.
- [x] Séparer le budget d'invocation du budget d'une étape Monty.
- [x] Borner les caches process-wide de regex, templates et clients HTTP.
- [ ] Borner et configurer la taille des réponses HTTP ; ces allocations Rust ne
      sont pas couvertes par le tracker mémoire Monty.
- Tester l'API bibliothèque comme une API publique, notamment sa configuration
    par défaut et les erreurs sans étape.
- Ne pas découper les gros modules uniquement pour réduire leur nombre de
    lignes : extraire les invariants ci-dessus, là où des divergences sont déjà
    observées.

- aucun finding majeur connu de correctness ou perte de données ;
- gates, e2e d'installation et plateformes distribuées verts ;
- contrat CLI/mold/registry/sandbox versionné et politique de dépréciation
    publiée ;
- plusieurs usages externes reproductibles, dont au moins un avec un registry
    partagé ;
- scope toujours conforme aux non-buts de `VISION.md`.

### Ce qu'il ne faut pas prioriser maintenant

- ajouter des formats ou built-ins parce qu'ils figuraient dans une ancienne
    liste ;
- présenter Fimod comme sandbox hostile, remplaçant universel de jq/yq ou Python
    complet ;
- bâtir un serveur, un index central ou une télémétrie réseau contraires à la
    vision.

## Limites de l'évaluation

- Pas de fuzzing systématique ni de mesure de couverture.
- Pas d'exécution Windows, macOS ou ARM pendant cette passe.
- Pas de mesure RSS dédiée sur HTTP, watch ou caches process-wide.
- Pas d'audit hostile du sandbox : la vision l'exclut explicitement.
- Les recherches de notoriété ne voient ni les dépôts privés ni les usages sans
    mention publique.
- Les chiffres publics sont un instantané du 10 juillet 2026 et évolueront.

## Conclusion

Fimod est déjà un **produit techniquement substantiel**, pas une démo : vision
claire, architecture réfléchie, documentation riche, centaines de tests,
release multi-plateforme et performance surveillée. Son wedge — petit couteau
suisse Python-shaped pour CI/config, HTTP et transforms partageables — est bon.

En revanche, sa surface fonctionnelle est aujourd'hui plus mûre que sa
fiabilité aux bords et très en avance sur son adoption. La décision rationnelle
pour le prochain cycle est donc : **geler l'expansion, fermer les findings de
fiabilité, rétablir une documentation exacte, puis obtenir des preuves d'usage
externes avant de choisir les prochaines features et avant 1.0.**
